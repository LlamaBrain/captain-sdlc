# Independent review schemas

`premerge-review-v1.schema.json` documents the snake_case JSON emitted by `Captain.Core/PremergeRecords.cs`, `Captain.Core/PremergeFindingLifecycle.cs`, `Captain.Core/ReviewImpactAnalyzer.cs` and the scanner envelope in `Captain.Orchestrator/ReviewScanners.cs` in captain-orchestrator. The root describes a persisted signed PR review record; definitions also cover snapshots, policy, findings, evidence, finding lifecycle, acceptance/implementation analysis, scoped exceptions and the trusted SARIF envelope. Nested history entries inherit their record's version and are not standalone cross-tool records.

Use definition references such as `premerge-review-v1.schema.json#/$defs/ReviewPolicy` when validating an individual contract. JSON Schema validates shape only. Core must additionally validate safe repository paths, actual source ranges/quotes, evidence digests and revision applicability, trusted provenance, corroboration of verified findings, allowed exception identities, timestamps, and deterministic policy. Orchestrator must authenticate stored records and recheck live PR identity. A structurally valid document cannot publish success by itself.

Schema version 1 corresponds to the current in-progress implementation, not a claim of shipped release compatibility. Keep this declaration aligned with implementation records; additive/breaking contract changes follow Captain's schema/version conventions. No executable review service or plugin policy is implemented in this documentation repository.

The bounded `ReviewImpact` report carries provenance, changed paths, textual symbol/public-contract candidates, possible callers/tests, module/configuration/persistence surfaces and explicit coverage limits. It is not a complete semantic graph and does not ship shared Interrogate code-reading tiers. `PrReviewRecord.elapsed_ms` records measured elapsed time; `reported_cost_usd` is nullable when the provider supplies no cost. A null cost is unknown, not zero.


`PrSnapshot.provenance` and `PrReviewRecord.provenance` identify input collection and authoritative review generation. The persistent review records and SARIF envelope explicitly require `schema_version` during deserialization; an omitted version is not implicitly version 1.

The `ReviewRemediationAttempt` and `ReviewRemediationResult` definitions document the optional library correction-loop reports from `Captain.Orchestrator/ReviewRemediationRunner.cs`. Each has an explicit version; nested attempts inherit task/run/provenance from the result. The result retains the independent review plus attempt outcomes and elapsed time, while nested `EvidencePacket` uses the existing Core evidence contract. Local `ReviewRemediationOptions` is a caller-owned invocation object rather than a new persisted cross-tool record and is deliberately not declared as a separate shared schema. These shape declarations do not claim CLI automation, persisted correction-loop reports, or a completed live remediation run.

## Actual execution and commit-status scope

Optional `PrSnapshot.test_merge_sha`, `open_head_pr_numbers` and `status_scope_provenance` capture the current test-merge revision and complete open-PR set sharing a head. GitHub commit statuses have repository/SHA/context scope rather than PR-number scope. Core rejects unknown or incomplete scope and requests human review when several open PRs share the head. The adapter rechecks the live scope and revisions before publication/readiness; it requires `github-open-pr-set/1` collector provenance. These checks narrow races without providing an atomic GitHub PR-scope transaction.

`ReviewEvidence.scope` distinguishes `head_only` and `head_and_base` observations. Explicit scopes record the actual `tested_sha`. Head-only evidence carries an empty `base_sha` and cannot satisfy required base-bound verification. Legacy evidence omits both scope and tested SHA while retaining its full base binding. Base-bound evidence requires the full current base and an applicable tested head or authenticated test-merge revision. JSON Schema expresses these shape cases; Core and the adapter establish revision equality, actual test-merge parents and trusted producer observations. A green author-head check does not acquire an untested base claim from PR metadata.

## Retained finding lifecycle

Optional `PrReviewRecord.finding_lifecycle` keeps known verified defects and their confirmation/resolution receipts inside the signed record. Missing reports, moved lines, optional scanner failure and new suppressions do not establish correction. Resolution requires an explicit current trusted receipt in `resolved_finding_ids`, with matching producer provenance, version, configuration and applicable confirmation scope. Head-only resolution cannot clear a base-bound confirmation. A policy-enabled exact-fingerprint human exception remains separately auditable and does not erase the defect.

`FindingLifecycleEntry` and `FindingLifecycleResult` emit `schema_version: 1` and `captain-core-finding-lifecycle/1` provenance. Entry contains the original finding, open/resolved lifecycle state, confirmation revisions, producer identity/configuration, optional `confirmation_scope` and nullable resolution receipts. Legacy confirmation revisions or producer metadata may be unavailable; preserving those values does not establish resolution authority. Only confirmation scope is omitted when null within an entry; producer configuration and resolution fields serialize explicit null. Result contains entries, unresolved blocking identifiers and errors. It is a reconciliation DTO whose current version property is emitted but is not marked `[JsonRequired]`; this shape declaration does not claim strict deserialization enforcement for that nonpersisted result.

The trusted collector must preserve the external tool's real analysis scope, configuration and baseline. Matching CIR adapter configuration alone does not establish that fact. JSON shape and provenance text do not replace collector isolation, source/evidence validation or deterministic policy.

## Compatibility and policy-engine identity

The new optional snapshot/evidence/ledger fields omit null to retain legacy signed record serialization. Keep historical artifacts unchanged; do not add defaults solely to make old evidence appear freshly captured. A schema-compatible old record must still be reconciled against current applicability.

Core fingerprints its own `captain-premerge-policy/2` engine identity independently of `ReviewPolicy.Version`. This invalidates earlier engine decisions even if operator policy remains `1`, so a cached old pass cannot survive corrected validation/deduplication semantics. Core validates every observation before deterministic risk-preserving deduplication. Wire schema version 1 remains distinct from the operator policy version and from the Captain plugin's documentation-run schema 2. No additional external schema-validation package is required by these declarations.
